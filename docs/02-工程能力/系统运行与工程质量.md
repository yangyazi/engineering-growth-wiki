# 系统运行与工程质量

## 能力定义

理解软件不只是一组源代码。它运行在特定的操作系统、运行时、网络、数据库、依赖、配置和部署环境中。工程质量意味着软件在真实环境中可验证、可诊断、可维护，并且失败时有明确处理方式。

## 需要建立的知识地图

| 范围 | 需要理解的核心问题 | 何时深入 |
|---|---|---|
| 操作系统与进程 | 程序如何启动、占用资源、读写文件、创建子进程？ | 遇到进程、资源或环境问题时 |
| 网络与协议 | 请求如何建立、传输、超时和失败？ | 遇到连接、超时和接口问题时 |
| 数据库 | 数据如何保存、查询、隔离和恢复？ | 遇到持久化、并发或查询问题时 |
| 并发与异步 | 任务如何并行，状态如何共享？ | 遇到竞争、吞吐和异步流程时 |
| 测试 | 如何证明行为符合预期？ | 每次功能变更都需要考虑 |
| 构建与部署 | 代码如何变成可运行的软件？ | 交付和环境差异出现时 |
| 可观测性 | 出问题时能否看见、定位和解释？ | 系统需要稳定运行时 |

## 工程质量不是“代码看起来整齐”

一个功能至少需要考虑：

- **正确性**：正常输入和边界输入下是否符合需求？
- **可测试性**：关键行为能否通过自动化或可重复实验验证？
- **可诊断性**：失败时有没有足够上下文定位问题？
- **可维护性**：修改一个功能是否需要理解大量无关代码？
- **安全性**：是否正确处理权限、敏感数据和外部输入？
- **运行可靠性**：失败、重试、恢复和版本回退是否有明确策略？

## 学习原则

不要求一开始成为操作系统、网络或数据库专家。先形成基本机制认知，再结合实际项目中的现象深入。对于不属于自己负责边界、缺少访问权限或无法验证的系统，不必强迫自己追完整条底层链路；要清楚边界在哪里，以及自己的模块依赖什么契约。

## 能力验收信号

能说明自己的程序如何启动、依赖哪些外部条件、如何配置和测试、失败时在哪里观察、修改后如何验证和交付。
