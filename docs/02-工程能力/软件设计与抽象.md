# 软件设计与抽象

## 能力定义

软件设计不是提前画一张漂亮架构图，而是根据需求、变化、约束和复杂度，决定如何组织代码与模块，让系统更容易理解、验证、修改和维护。

## 需要逐渐形成的判断

### 职责与边界

- 一个模块负责什么、不负责什么？
- 这个逻辑应该放在哪里？
- 两个模块为什么需要相互依赖？这种依赖是否必要？
- 一个变化发生时，影响范围是否可控？

### 抽象与复用

- 哪些逻辑真的重复，值得抽象？
- 抽象是否隐藏了复杂度，还是制造了更多间接层？
- 接口表达的是稳定能力，还是当前某个实现细节？
- 是否过早为不确定的未来需求设计？

### 方案权衡

- 简单实现是否已经足够？
- 复杂方案带来的收益能否证明其额外成本？
- 可扩展性、性能、可靠性和维护成本之间如何取舍？
- 方案是否符合团队现有技术栈和运行约束？

## 通过真实代码训练设计能力

不要先背一套设计模式，再到项目里到处套用。更有效的做法是：

1. 找到一个现有功能，理解它当前的职责划分。
2. 观察一次需求变化会迫使哪些代码一起修改。
3. 识别修改困难的原因：职责混杂、依赖方向不合理、接口不稳定，还是缺少测试？
4. 提出至少两种可行设计，并写清各自的复杂度与代价。
5. 选择适合当前约束的方案，做小范围改动并验证。

## 需要避免的误区

- **把分层当作设计本身**：有 Controller / Service / Repository 不代表设计合理。
- **把抽象越多当作越高级**：不必要的接口、工厂和层级会增加认知负担。
- **把可扩展性当作无成本**：为尚不存在的变化做过度设计，可能让当前系统更难理解。
- **照抄 AI 的架构建议**：AI 给出的方案必须放回真实上下文中评估。

## 能力验收信号

能够针对一个实际需求，给出清晰的模块边界、数据和接口设计，比较替代方案，并解释为什么当前选择在现有约束下更合适。
