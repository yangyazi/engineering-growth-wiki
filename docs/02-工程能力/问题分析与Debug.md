# 问题分析与 Debug

## 能力定义

Debug 不只是看报错和修改代码，而是面对不符合预期的行为，使用可验证的假设和证据缩小问题范围，找到根因，并确认修复没有引入新问题。

## 通用诊断流程

```text
描述现象
  ↓
明确预期与实际差异
  ↓
收集证据（日志、输入、状态、调用链、环境）
  ↓
提出多个可能原因
  ↓
设计最小验证实验
  ↓
逐步排除，定位根因
  ↓
修复并增加回归验证
  ↓
复盘：如何更早发现？
```

## 从“猜原因”转成“验证假设”

假设某项功能结果不正确，不要立刻接受“可能是正则表达式的问题”或“可能是数据库的问题”。先列出候选原因，并明确每个原因需要什么证据。

| 假设 | 需要观察的证据 | 可执行的验证 |
|---|---|---|
| 输入数据发生变化 | 原始输入样本、格式分布 | 比较异常前后的输入 |
| 解析逻辑漏掉部分情况 | 解析成功率、未匹配样本 | 用异常样本写最小测试 |
| 中间请求失败 | 请求状态、超时、重试记录 | 复现请求并记录完整响应 |
| 存储端写入不完整 | 写入条数、事务结果、数据库记录 | 对比写入前后的数量与主键 |
| 展示或查询逻辑有问题 | API 响应、查询条件、前端状态 | 绕过界面直接检查接口结果 |

这张表只是说明方法，不代表任何具体问题一定发生在这些环节。

## 训练方式

- 选择一个真实且边界清晰的问题，先自己写出初始假设。
- 通过日志、断点、测试、指标或最小复现收集证据。
- 每次只验证一个假设，避免同时改很多地方。
- 在修复前保存能稳定复现问题的输入或测试。
- 修复后增加回归测试，防止问题再次出现。

## AI 在 Debug 中的正确位置

可以让 AI 帮忙列出候选原因、解释堆栈、建议观察点或审查推理。但必须提供实际证据，并区分：

- 已经观察到的事实；
- 基于事实提出的假设；
- 尚未验证的猜测；
- 最终确认的根因。

## 能力验收信号

面对陌生故障，能够独立描述现象、列出并排序假设、设计验证步骤、引用证据说明根因，并通过回归测试证明修复有效。
