# 工程训练总览

训练场是一个真实代码库，而不是课程表。为什么这样选，见[为什么选择真实代码库](为什么选择真实代码库.md)。

## 为什么改变训练主线？

前面讨论过简单的日志解析器、任务管理系统等练习。这些可以训练入门语法或局部功能，但不足以单独解决当前最核心的成长问题：缺少在有历史代码、模块依赖、测试约束和真实变化下参与软件工程的经验。

因此，长期训练的核心应该是一个**有一定复杂度、真实代码结构、可运行、可测试、持续维护的软件项目**。

不是为了“做完一个项目”，而是把它当成训练环境，反复练习理解、设计、修改、诊断、重构和交付。

## 五种基本训练活动

| 活动 | 要练习的能力 | 典型产出 |
|---|---|---|
| 阅读和追踪 | 代码理解、系统认知 | 调用链、数据流、模块说明 |
| 设计和评审 | 抽象、技术判断 | 需求拆解、方案比较、设计记录 |
| 功能修改 | 构建、工程协作 | 可审查的代码变更和测试 |
| Debug 与实验 | 假设、证据、根因分析 | 可复现用例、排查记录 |
| 重构与验证 | 质量、维护性 | 重构对比、回归测试、风险说明 |

## 训练不是固定课程表

每一轮训练由一个明确的工程问题驱动。遇到网络问题时，再深入网络机制；遇到事务问题时，再研究数据库；遇到复杂依赖时，再学习模块化和设计原则。

这并不意味着不学习基础知识。基础知识会围绕训练问题系统补齐，而不是与工程实践分离。

## 训练的边界

- 项目要足够真实，但规模不能大到无法建立局部理解。
- 每轮任务要有清晰边界和可验证结果。
- AI 可以协助，但自己必须保留初始判断和验收过程。
- 不要求每次都修改代码。有时高质量的代码阅读、实验或故障分析就是有效训练。
