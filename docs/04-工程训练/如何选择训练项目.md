# 如何选择训练项目

当前尚未最终选定项目。选择时不要只看 GitHub Star 数或技术栈热度，应重点看项目是否适合持续训练。

## 项目筛选条件

| 维度 | 理想特征 | 为什么重要 |
|---|---|---|
| 代码结构 | 有多个清晰模块，而不是单文件脚本 | 训练阅读、抽象和模块边界 |
| 功能完整度 | 有真实用户场景和核心业务逻辑 | 训练需求理解和功能修改 |
| 可运行性 | 文档清晰，能在本地或容器中运行 | 能够观察真实行为 |
| 测试体系 | 有单元测试或集成测试 | 能够验证自己的理解和变更 |
| 外部依赖 | 有 API、数据库或其他组件，但可控 | 接触真实系统边界 |
| 问题与历史 | 有 Issue、PR、版本记录或维护讨论 | 观察真实问题如何解决 |
| 规模 | 可以从小模块切入 | 避免一开始被全仓库淹没 |
| 许可 | 许可证清晰，允许学习和修改 | 避免版权和使用边界不清 |

## 语言应该如何选择？

当前已有一定 Python 使用基础，因此优先考虑 Python 项目能降低语言切换成本。但项目选择不应被 Python 永久限制。核心目标是学习可迁移的软件工程能力，而不是把职业方向锁定在某种语言。

## 优先考虑什么类型？

可以先从具有真实业务逻辑的开发工具、开发者服务、API 服务或中等规模应用中筛选。它们通常能同时看到接口、数据模型、核心逻辑、测试和运行方式。

不建议一开始选择：

- 超大型底层基础设施项目，内部机制和构建门槛很高；
- 只有少量代码的教学 Demo，缺少真实工程关系；
- 依赖大量外部云服务、无法在本地验证的项目；
- 文档和测试极少、维护状态不明的仓库；
- 只因为热门而选择、自己并不关心其问题域的项目。

## 选择之后先做什么？

不要立即安排开发功能。先验证：

1. 能否按官方文档成功运行项目？
2. 能否运行至少一组测试？
3. 是否能找到一个从入口到结果的核心功能？
4. 是否能识别一个适合新手切入的局部模块？
5. 是否能在不破坏主分支的前提下创建独立实验分支？

只有这些条件基本成立，才进入长期训练。
